# 持续生成、评测与修改

这是维护技能时使用的流程。普通 UI 任务仍按 `SKILL.md` 执行，不必每次搭建一套评测环境。

每轮都留下技能版本、原始需求、实际产物和评审结论。完成一轮只代表这轮有结果，不代表跨平台设计能力已经验证完毕。

维护交付先说明技能中哪条判断改变了、为什么改变、验证是否支持；案例代码修复单独记录。只有案例数量、日志或测试通过数增加时，不称为技能已经完善。

## 生成时固定输入

把技能保存为快照，记录提交号和文件哈希。给案例生成者真实、简短的产品需求、目标平台与运行条件，不附预期答案、怀疑的问题或上一轮修法。生成者按快照读取技能，完成参考图、实现和验收，并保留最初可运行版本。

轮换内容和操作特征，例如阅读、检索、比较、编辑、确认、恢复失败操作。网页、App、小程序、桌面、游戏和组件分别记录目标平台与实际运行环境。浏览器中的手机尺寸不算原生 App，开发工具模拟也不算真机验证。

案例需求可以包含必要的长文本、空结果、错误、费用、风险或状态。它们用于检验信息取舍，不能提前把某种构图或要找的缺陷写进提示。

## 用成品作判断

条件允许且已获授权时，由另一位评审者只看原始需求、实际界面和必要的行为证据，先不看生成者自评或技能改动。没有独立评审时如实记录为自查。

给评审的源码和截图也固定为同一产物快照。评审期间的修正另存新版本；不要让旧截图与正在变化的源码混成一个验收对象，记录各自的文件哈希和对应关系。

评审要实际查看截图；涉及操作的判断还需要相应运行证据。每个问题写清所在位置、用户影响和证据。没有证据就标记未知；个人偏好与违反需求的缺陷分开，不要求凑够问题数量。

先实测触发问题所需的状态，再判断操作结果。例如检查换篇滚动时先确认页面确实已滚动；检查窄屏时核对实际布局画布，不能从设置尺寸的调用或截图文件名推断。逻辑尺寸、设备像素比和图片导出倍率分开记录，测试宿主的适配错误与产品错误分开保留。

检查这些方面即可，按案例选择，不合成一个“精美度总分”：

| 方面 | 要看什么 |
| --- | --- |
| 任务与信息 | 主内容和操作是否清楚，必要信息有没有被删，无用信息是否占位 |
| 构图与细节 | 比例、对齐、排版、颜色和素材是否形成统一关系 |
| 文字 | 动作与状态是否准确，是否有空话、重复解释或无依据的承诺 |
| 平台与输入 | 控件、导航、触控、键盘或控制器行为是否符合该任务 |
| 内容增长与状态 | 长内容、窄窗口、失败和恢复是否仍然可用 |
| 跨案例差异 | 不同任务是否导出了不同结构；同一品牌下合理的复用是否被保留 |

运行测试数量只说明覆盖了哪些行为，不能换算成审美分数或“去 AI 味百分比”。

## 从问题回到技能

先判断问题出在哪一层：需求缺失、生成参考、技能的决策指引、实现偏差、测试遗漏，还是合理取舍。修好一个图标或一段代码，不自动构成一次技能提升。

只有现有指引确实没有帮助模型作出正确判断时，才修改技能。记录“可见问题 → 原指引的缺口 → 修改位置 → 希望改变的决定”。优先改清楚已有表述；不把案例中的颜色、布局和控件数量写成通用要求。

改动后，让新的生成过程使用新快照处理同一需求，并用一个未参与修法的案例检查副作用。保留前后结果；没有改善就撤回或缩小改动。生成有随机性，单次前后差异不能证明所有任务都会变好。

## 保存证据

每轮记录案例需求、技能快照、构建及运行环境、参考图、实际截图、操作结果、评审、接受或放弃的修改、回测和未覆盖范围。

可用 [collect_evidence.py](collect_evidence.py) 收集并计算文件哈希。它只证明收集了哪些文件，不判断设计质量，也不把声明的版本号当成已验证的版本来源。

原始产物保留在隔离目录；选择有代表性的对照图入仓。依赖目录和缓存不作为评测证据。失败案例也要保留，避免只展示成功结果。

只保留能说明问题与改动的必要证据和可追溯位置，不让整套运行日志、重复截图或大体积测试产物占据技能更新的主体。
